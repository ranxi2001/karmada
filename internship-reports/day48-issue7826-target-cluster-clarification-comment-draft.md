One clarification about the code that appears to hard-code `member1` as the target.

[`targetClusterNames`](https://github.com/karmada-io/karmada/blob/3d4d14d746de507164abf40c1017b1f2b0e47e3a/test/e2e/suites/base/tainttoleration_test.go#L140-L146) is not written into the policy. The test reads the current `ResourceBinding` through `ExtractTargetClustersFromRB` and only asserts that the result has exactly one entry equal to `tolerationValue`, which is [`framework.ClusterNames()[0]`](https://github.com/karmada-io/karmada/blob/3d4d14d746de507164abf40c1017b1f2b0e47e3a/test/e2e/suites/base/tainttoleration_test.go#L47-L64). The actual policy candidate set is still [all `framework.ClusterNames()`](https://github.com/karmada-io/karmada/blob/3d4d14d746de507164abf40c1017b1f2b0e47e3a/test/e2e/suites/base/tainttoleration_test.go#L66-L77). The initial result is `{member1:3}` because only member1's taint is tolerated, not because the policy permanently restricts the binding to member1.

After the assertion passes, [`AfterEach` removes the taints from every candidate cluster before `DeferCleanup` deletes the Deployment and policy](https://github.com/karmada-io/karmada/blob/3d4d14d746de507164abf40c1017b1f2b0e47e3a/test/e2e/suites/base/tainttoleration_test.go#L104-L137). In the [official job](https://github.com/karmada-io/karmada/actions/runs/28998390044/job/86054168911), the same `deploy-wbch9-deployment` was requeued by `ClusterChanged` at `07:10:24.146`, became feasible on all three clusters at `.170`, was assigned `{member1:3, member2:3, member3:3}` at `.195`, and was patched at `.239`. After that successful patch, [`patchScheduleResultForResourceBinding`](https://github.com/karmada-io/karmada/blob/3d4d14d746de507164abf40c1017b1f2b0e47e3a/pkg/scheduler/scheduler.go#L683-L775) records an assumption for every cluster in the new result.

This does not mean that the Deployment finished propagating or ran on member2/member3. The bug is that the assertion passed, but cleanup changed its scheduling precondition while the old binding still existed. That allowed the binding to be rescheduled and its in-flight assumptions to be refreshed before deletion; later estimator requests then consumed those residual assumptions.

Executive answer

Deployment 支持，不只是一条 GVK 白名单

5 层类型 · 归属 · 状态 · 放置 · 执行
≠

工作负载（workload）

需要被调度、运行并持续维护的资源对象。

副本（replica）

B

04 / 方案 C + D复杂类型有两个改造方向：扩核心，或委托执行14 / 16

Native model vs delegated execution

组件向量进核心，状态语义留给 operator

C / D一个改表示，一个改执行边界
C

原生组件感知的 Binding / scheduler 重构

让 Karmada 核心直接表达并重新分配逐集群组件向量，适合明确需要跨集群组件级分布的产品目标。

apis/work/.../binding_types.go扩 TargetCluster 的 per-component assignment。
estimator.proto返回 component deficits，不再只有 int32。
scheduler/core组件级 estimation、division、scale / reschedule。
binding controller增加类似 ReviseComponents 的应用契约。
generated / CRD / migration生成代码、OpenAPI、兼容读写与升级测试。
覆盖较广、核心改动最大；仍不能单独解决 checkpoint / ordinal 等领域语义。仅在产品确认组件级跨集群分配后启动。
D

核心给计划，已注册执行方完成迁移

Descheduler 输出候选；scheduler 选目标；adapter、Operator 或存储控制面负责 checkpoint、ordinal、gang 与完成确认。没有执行方时保持不支持。

D1 · GracefulEvictionTasks扩展现有 embedded task；已有 source、preserved state、health / timeout，仍缺独立 status 与 work-unit identity。
D2 · new task CRD独立 status 和重试更清楚，但增加 controller、RBAC 与升级成本。
WorkloadRebalancer可作为显式 intent 入口；不能与 Descheduler 各自写 Binding。
pkg/scheduler仍负责目标集群选择，不接管应用状态机。
execution provider显式实现 prepare、target-ready、cutover、rollback。
安全上限高，但取决于执行合同和真实执行方；Job / StatefulSet 不会天然获得跨集群迁移能力。

本页回答C 解决核心表示，D 解决领域执行；两者不能互相替代。

06 / 推荐路线先定义支持边界，再逐层扩大16 / 16

Phased delivery

从“可替换标量”交付，向“领域迁移任务”演进

B → DA 过渡 · D/C 按条件启动
PHASE 0 / CONTRACT

先划能力边界

定义 T0/T1/T2、opt-in、dry-run、预算、唯一写入方与拒绝原因。

PHASE 1 / A → B

交付一个受控 adapter

用 A 验证额外 T0 类型，但接口按 B 定型，避免继续堆 switch。

PHASE 2 / D GATE

先定执行方与任务载体

T0 继续走 B；复杂类型先比较 embedded task / 新 CRD，并确认谁执行完成协议。

PHASE 3 / C GATE

产品需要时再改 Binding

只有确认跨集群逐组件分配价值，才启动 API 与 scheduler 联动重构。

Q1 / WHY DEPLOYMENT

首版闭合了最小纵向切片

事实 已核查材料的示例和首版实现都以 Deployment 为边界；推断 它的四个计数可压成同一个可替换标量。

Q2 / WHY NOT ALL GVK

五层契约必须一起成立

类型准入、Pod 归属、运行状态、放置表示、执行完成，任一层缺失都会把“重调度”变成不安全缩容。

Q3 / WHICH ROUTE

B 先落地，D/C 按条件启动

B 承担可替换标量通用化；D 先确认执行方和 task 载体；A 仅过渡，C 等组件级需求确认后再投入。

本页回答交付目标应写成能力类别（capability class），不写成“支持所有资源类型”。

汇报收束先证明语义可迁移，再让代码接受新的 GVK。

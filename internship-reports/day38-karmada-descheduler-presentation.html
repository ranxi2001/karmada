01 / CORE IDEA

它不是第二个 scheduler

Descheduler 只把失效旧分配变成一个普通副本缺口；新位置仍由 scheduler 决定。

运行态事实 某集群的部分 Pod 长期 Unschedulable
→
减少源分配 Binding 6 → 4；状态可信时不低于 Ready
→
Steady scale-up scheduler 补齐缺少的 2 个副本

检测旧分配失效，与决定新分配位置，是两种不同职责。

03 / HISTORY

Deployment-only 是窄 MVP 的结果，不是通用结论

2021-09 Issue #697 很宽

既谈资源不足，也谈新集群加入后的利用率均衡。

2021-11 KEP 只保留 Story 1

只处理资源不足造成的长期 Unschedulable Pod。

2022-02 按 Deployment 闭环

首版实现围绕 replicas、Ready 和 owner chain 落地。

至今 通用抽象仍未完成

GVK、abstract workload、custom Ready interpreter 仍留有边界。

准确说法：当时只实现了一个 Deployment 长期放不下的最小故事。

Evidence: Issue #697, KEP-697, PR #726, PR #1392

04 / WORKLOAD SEMANTICS

不是多加一个 GVK，而是要先定义“一个副本”

Deployment
  • replicas单一期望副本数
  • readyReplicas成功反射时可作为运行下界
  • owner UID能定位本轮 rollout 的 Pod
  • replaceable副本通常彼此可替换
StatefulSetordinal、PVC、稳定身份，换集群不等于迁移数据
Jobcompletion、index、重试与幂等，减副本可能重复执行
FlinkDeployment多组件与 checkpoint，一个 Binding 标量不够表达
AI workloadleader、worker、gang、shard 与拓扑关系不能拆成任意 Pod

扩 Kind 之前，必须先有 replica、Ready、ownership、source shrink 四个合同。

08 / QWEN SCOPE

先确认四个前提，再决定是不是 Descheduler

Issue/PR 与官方书面纪要未确认 Qwen/GPU；公开会议录像的本地 ASR 提到 Spot GPU，但不能绑定具体产品。

适用前提（待内部确认）

01离线且允许中断
02部分 Pod 长期 Unschedulable
03replica 可被同类实例替换
04接受只恢复 assignment，不要求 target Ready

当前方案不够

01在线流量、服务不能中断
02warm-up、checkpoint、数据搬迁
03leader、worker、shard、gang
04必须 target Ready 后才能删 source

右侧任一条件成立，就需要 workload-aware migration 合同，不能只靠当前 Descheduler。

09 / LIMITS

真正限制扩展的，不是策略数量

01 / WORKLOAD

工作负载语义

当前固定 Deployment；多组件、身份、完成进度和数据状态无法映射为一个标量副本缺口。

02 / SIGNAL

信号与归属

必须准确定位本轮 workload 的 Pod，并区分真实长期不可调度、发布中和暂态抖动。

03 / SAFETY

安全与策略

缺少 release budget、dry-run 和统一安全层；readyReplicas 缺失时记为 -1，不会自动停止缩减。

04 / OWNERSHIP

一致性与 single writer

Descheduler、scheduler、Rebalancer 不能同时独立修改同一 Binding，完成条件也必须唯一。

先建立安全骨架和 ownership，再谈多 Kind、多策略。

10 / DIFFERENT LAYERS

名字相同，处理的调度单元不同

Kubernetes：Pod → Node

统一对象、标准 Eviction API、PDB 和 owner controller。

Karmada 平台：Binding(GVK) → Cluster

当前只修正 per-member Deployment target/count，不携带具体 Pod identity。

因此不能按插件数一比一复制

值得借鉴的是框架与安全机制，不是直接照搬 Node 级策略。

Canonical source: day38-karmada-vs-kubernetes-descheduler.mmd

12 / RECOMMENDATION

借框架，不抢 scheduler 的目标选择权

PHASE 0

把窄场景做稳

明确 opt-in、长期 Unschedulable、replaceable replica、已知 Ready 下界和唯一完成条件。

PHASE 1

先抽安全骨架

增加 dry-run、release budget、strategy/reason metrics，以及统一 Binding mutation executor。

PHASE 2

再扩 workload

定义 resolver 合同和 support matrix；多组件先解决 per-component placement，不宣称 any workload。

最终原则：Descheduler 把旧 target 异常转成数量缺口，scheduler 始终决定新位置。

WORKLOAD SEMANTICS

不是多加一个 GVK，而是先定义“一个副本”

4个合同必须同时成立
REFERENCE CASE

Deployment

  • replicas单一期望副本数
  • readyReplicas成功反射时可作运行下界
  • owner UID定位本轮 rollout 的 Pod
  • replaceable副本通常彼此可替换
STATEFULSET

身份合同不同

ordinal、PVC、稳定身份存在，换集群不等于数据已经迁移。

JOB

完成合同不同

completion、index、重试与幂等存在，减副本可能造成重复执行。

FLINKDEPLOYMENT

组件合同不同

多组件与 checkpoint 存在，一个 Binding 标量无法表达各组件 placement。

AI WORKLOAD

拓扑合同不同

leader、worker、gang、shard 关系不能拆成任意可替换 Pod。

结论扩 Kind 之前，必须先有 replica、Ready、ownership、source shrink 四个合同。

CURRENT LIMITS

真正限制扩展的，不是策略数量

4类工程合同缺口
01

工作负载语义

当前固定 Deployment；多组件、身份、完成进度和数据状态无法映射为一个标量副本缺口。

02

信号与归属

必须定位本轮 workload 的 Pod，并区分真实长期不可调度、发布中状态和暂态抖动。

03

安全与策略

缺少 release budget、dry-run 和共享安全层；Ready 缺失时是 -1，不会自动 fail-closed。

04

一致性与 single writer

Descheduler、scheduler、Rebalancer 不能独立争写同一 Binding，完成条件也必须唯一。

优先级先建立 safety、ownership 与 completion，再谈多 Kind、多策略。

下一问这些限制难补，不只是实现量大，而是 Karmada 与 Kubernetes 的调度单元根本不同。

RECOMMENDATION

借框架，不抢 scheduler 的目标选择权

3阶段演进路线
PHASE 0先做稳

收紧窄场景

明确 opt-in、长期 Unschedulable、replaceable replica、已知 Ready 下界和唯一完成条件。

PHASE 1再做安全

抽共享骨架

增加 dry-run、release budget、strategy / reason metrics，以及统一 Binding mutation executor。

PHASE 2最后扩展

逐类支持 workload

定义 resolver 合同和 support matrix；多组件先解决 per-component placement，不宣称 any workload。

最终原则：Descheduler 把旧 target 异常转成数量缺口，scheduler 始终决定新位置。

完整证据报告

TAKEAWAY先解决 safety、single writer 与 completion，再讨论通用 workload。

汇报收束回答问题时始终回到同一主线：Observe → Release → Place。
